## 付録 A:コストを動かすのはキャッシュ

この付録のポイントは、コストを最も動かすのはキャッシュだということです。毎ターン送り直す会話の前半が、割安なキャッシュから読まれる割合を「命中率」と言います。同じ約 280 万 input token の作業が、キャッシュなしで $11.20、命中率 90% で $1.62、96% で約 $0.99 になり、約 11 倍違います。原文でも、入力コストをこれほど動かす設定は他にない、と述べています。ツール定義やシステムプロンプトなど、会話の前半を書き換える操作は命中率を下げるので注意が必要です。

もう 1 つ、effort は「抜け漏れ」を減らしますが「方向違い」は直せない、というのが著者の主な結論です。

<sub>出典: https://claude.dev/blog/spending-your-effort/ / https://claude.dev/blog/what-a-task-costs-on-opus-5-5/</sub>

## 付録 D:GCC オラクルと delta debugging

**Q.** なぜ大半を GCC でビルドするのか。自作コンパイラで問題を見つける意味は?

**A.** このプロジェクトの目的は「自作コンパイラ」そのものを正しくすることです。GCC は何十年も使われてきた既知の正解で、Linux カーネルも GCC でビルドされています。カーネルは数万のファイルを全部正しくビルドしないと起動しないので、全部を自作でビルドして壊れても、どのファイルが原因か分かりません。そこで、大半を GCC でビルドし、少数のファイルだけ自作でビルドします。壊れたなら、原因は自作側の少数のファイルの中にあります。agent ごとに別の少数のファイルを担当すれば、並列に別々のバグを直せます。直るにつれて自作の割合を増やし、最終的に全部を自作でビルドしました。具体的な割合は原文に書かれていません。

**Q.** delta debugging とは。

**A.** 失敗する入力や変更の集合を、半分ずつに分けて試し、最小の失敗原因に絞り込む手法です(一般的な知見)。git bisect はコミット単位の二分探索で、関連の深い考え方です。ここでは、単独では動くのに組み合わせると失敗するファイルの対を特定するのに使われました。merge conflict の解決ではありません。

<sub>出典: https://www.anthropic.com/engineering/building-c-compiler</sub>

## 付録 E:evaluator の「失敗」基準

**Q.** evaluator はいつ失敗と判定するのか。基準は?

**A.** 記事には 2 つの場面があります。前端のデザイン実験では、設計品質・独創性・完成度・機能性の 4 基準で採点し、設計品質と独創性を重く扱いました。5〜15 回反復する実験で、合否の判定はありません。

完全なアプリを作る harness では、evaluator が Playwright で UI、API、データベースの状態まで実際に操作し、製品の深さ、機能性、視覚デザイン、コード品質の観点で採点します。各基準に硬い閾値があり、1 つでも下回ると、その sprint は失敗として generator に詳細なフィードバックが返ります。sprint の前に「完了の定義」を合意し、ある sprint では 27 項目の基準がありました。閾値の具体的な数値は記事に書かれていません。

校正は、点数の内訳つきの few-shot 例と、ログを読んで人間の判断とずれた点を prompt に反映する作業を数回繰り返して行いました。Opus 4.6 以降は sprint 構造を外し、評価は最後に 1 回です。

<sub>出典: https://www.anthropic.com/engineering/harness-design-long-running-apps</sub>

## 付録 F:別 session・別モデルでの評価

**Q.** 別 session でも自己採点は甘くなるか。Gemini など別モデルに評価させれば大丈夫か。

**A.** 別 session にすると、自分が書いたものを守る文脈のバイアスは減ります。ただ公式記事は、分離しても評価者は LLM であり、LLM が作ったものに寛容になりやすいと述べていて、同じモデルの evaluator は懐疑的になるよう調整する必要がありました。

別モデルに評価させるのは良い習慣で、自分のスタイルを好む偏りは減ると考えられます(一般的な知見で、公式記事の主張ではありません)。ただ、評価者としての寛容さや、似た誤りを共有する可能性は残ります。ですから、別モデルの評価は追加の信号として使い、最も強いのは実行して確かめられる検証(テスト、ビルド、再現)だと考えています。

評価を頼むときは、元の要件も渡す、誰が書いたかは伏せる、「問題を探す」という役割にする、点数ではなく具体的な基準で見る、の 4 点を意識します。

<sub>出典: https://www.anthropic.com/engineering/harness-design-long-running-apps / https://code.claude.com/docs/en/best-practices</sub>

## 付録 G:校正(few-shot)と過剰指摘の防止

**Q.** 校正(few-shot)とは何か。

**A.** 評価者に、人間が点数と理由を付けた例を数個見せて、「この出来ならこの点」という基準を揃えることです。記事では、点数の内訳つきの例で評価者を校正し、反復の間に点数がぶれる現象を減らしました。コードレビューなら、「競合状態があるので blocker」という例と、「命名の好みは指摘しない」という例の両方を見せます。

**Q.** 過剰な指摘をどう防ぐか。

**A.** 公式文書には、「問題を探せと言われた評価者は、実装が正しくても何かしら報告する」とあり、すべてに対応すると、余計な抽象化や防御コード、起こり得ないケースのテストが増えて過剰設計になる、と注意しています。対策は 5 つです。①正しさと要件に影響する問題だけを対象にする。②場所、理由、再現方法の証拠と、根拠となる行の原文引用を必須にする。引用できなければ対象外です。③確信度を 10 段階で付けさせ、7 未満は修正必須にしない。件数の上限は 5 件とし、削った件数は報告させる。④指摘すべき例としない例、それに「指摘しないリスト」で校正する。⑤指摘を別の subagent が反駁できるか確認し、修正は 1〜2 回で止める。

①と⑤の前半は公式の推奨に沿っています。④の校正は harness 記事の方法です。②の原文引用と③の確信度、「指摘しないリスト」は、gstack の review skill を参考にした運用上の工夫で、件数の上限と⑤の後半も含めて公式の推奨ではありません。

<sub>出典: https://code.claude.com/docs/en/best-practices / https://claude.dev/blog/getting-the-most-out-of-opus-5-5/ / https://www.anthropic.com/engineering/harness-design-long-running-apps</sub>

## 付録 H:Mods のデモ Token Weather

実際の例が Token Weather です。コンテキストウィンドウの使用量を「天気予報」のようにプロンプトの上に表示する、約 80 行の mod です。構成は plugin.json、hooks.json、モジュール本体の 3 ファイルだけです。claude --plugin-dir で読み込み、ファイルを保存すると hot reload されます。validate と test のコマンドも用意されています。

使用量は session の usage で読み、状態は state に保存するので、hot reload をしても履歴が消えません。

重要なのは、これが特別な内部機能ではなく、誰でも同じ API で作れるということです。

<sub>出典: https://claude.dev/blog/getting-started-with-claude-code-mods/</sub>

## 本編から外した:並列化の壁と GCC オラクル

並列化には壁がありました。テストが独立している間は簡単で、各 agent が別々の失敗テストを担当すればよい。ところが Linux カーネルのコンパイルは「1 つの巨大なタスク」で、16 の agent が全員同じバグに当たり、同じ修正をして互いの変更を上書きしました。16 個動かしても、全員が同じ問題を解いていたわけです。

解決策が GCC をオラクルにすることでした。カーネルのファイルをランダムに選び、大半を GCC で、残りだけを自作コンパイラでビルドします。カーネルが動けば、自作側の担当範囲に問題はない。壊れれば範囲を絞る。これで各 agent が別々のファイルの別々のバグを同時に直せるようになりました。

最後に、単独では動くのに組み合わせると失敗するファイルの対があったため、そこは delta debugging で特定しています。補足ですが、delta debugging は「conflict の解決」ではなく「失敗の原因の絞り込み」に使われています。

一般化すると、並列化できない問題でも、「既知の正解」を使って問題を分割できないかを考える価値がある、ということです。

<sub>出典: https://www.anthropic.com/engineering/building-c-compiler</sub>

## 本編から外した:使い分けと、注意すること

最後に、使い分けと注意点です。session を動かし続ける方法は 3 つあります。/goal は、条件が満たされるまで。/loop は、時間の間隔で繰り返す。Stop hook は、自分のスクリプトか prompt で判定する。終点がはっきりした作業には /goal、決定論的に判定したいなら Stop hook です。auto mode は 1 ターンの中の tool の確認を省くもので、/goal はターンごとの確認を省きます。両方を組み合わせると、無人で回せます。

注意点です。評価者も LLM なので、寛大になることがあります。だから条件は、機械的に確かめられる形に書きます。tool を使わず進まないターンが続くと、Claude Code は警告を出して、制御を人に返します。認証エラー、クレジット切れ、コンテキストの溢れ、モデルが使えない、といった人が直すエラーでは、ゴールが解除されます。直してから、もう一度 /goal を設定します。細かい挙動は version で変わるので、手元の version を確認してください。

<sub>出典: https://code.claude.com/docs/en/goal</sub>

## 本編から外した:品質低下の原因は 3 つの小さな変更(4/23 事後報告)

4 つ目は失敗から学ぶ話です。4 月 23 日に Anthropic が、Claude Code の品質低下の報告について事後報告を出しました。原因はモデルではなく、製品側の 3 つの小さな変更でした。

1 つ目、3 月 4 日に、遅延を減らすため既定の reasoning effort を high から medium に下げました。「賢くなくなった」という声が続き、4 月 7 日に戻しています。

2 つ目、3 月 26 日のキャッシュ関連の変更です。1 時間以上アイドルしたセッションで古い思考を 1 回だけ消すはずが、バグで毎ターン消え続けました。そのせいで Claude が健忘で繰り返しに見え、使用量の消費も増えました。4 月 10 日に修正されています。

3 つ目、4 月 16 日に冗長さを抑える system prompt を足したところ、他の変更と合わさって品質が落ち、ある評価で約 3% の低下が出ました。4 月 20 日に戻しています。

教訓は 3 つです。既定値は性能調整ではなく品質の判断であること。長いセッションや再開したセッションも試験すること。prompt は 1 行ずつ外して効果を測ること。

<sub>出典: https://www.anthropic.com/engineering/april-23-postmortem</sub>
