## 2. 並列 agent(C コンパイラ事例)

出典: Anthropic Engineering「Building a C compiler with a team of parallel Claudes」(Nicholas Carlini、2026-02-05、研究プロトタイプ)

### 2.1 数字
16 agent、約 2,000 セッション、約 2 週間、約 $2 万、10 万行の Rust 製 C コンパイラ。Linux 6.9 を x86・ARM・RISC-V でビルドでき、主要なテストスイートの 99%。使用モデルは Opus 4.6、クリーンルーム(インターネットなし)。
**注意**:数字は当時のモデルでの結果。「研究者の実験報告」であり、製品の標準的な使い方ではない。

### 2.2 「10 万行 Rust 製コンパイラ」とは
Rust で書かれた **C 言語のコンパイラ**(約 10 万行)。入力は C(Linux カーネルも C)、実装言語が Rust。コンパイラが少しでも間違うと起動可能なカーネルが作れないので、厳しいストレステストになる。

### 2.3 オーケストレーターとは
複数の agent を動かすとき、**仕事を割り振る「管理役」**。4 つの仕事をする:タスクの分解、割り当て、順序づけ、結果の回収と失敗時の再割り当て。

| オーケストレーターの仕事 | この事例で代わりに担ったもの |
|---|---|
| タスクを分解し一覧にする | 失敗しているテスト(これは筆者の整理で、原文の言葉ではない) |
| 割り当て | 各 agent が「次に最も明らかな問題」を自分で選ぶ |
| 重複を防ぐ | `current_tasks/` の lock ファイル + git の同期 |
| 順序づけ | ほぼ不要(テストが互いに独立) |
| 結果の回収 | 各 agent が merge して push |
| 失敗後の再割り当て | テストが通るまで次の agent が続きを拾う |

原文:「I don't use an orchestration agent」。ただし**環境(lock・テスト)がその役を担っている**のであって、調整が全く無いわけではない。
**条件付き**:タスクが独立に分けられ、テストが「どこが壊れているか」を教えてくれる場合に成立する。カーネルのように 1 つの巨大タスクで切り分けできないと、16 agent が同じバグを直して上書きし合った(原文)。そこで GCC を使った分割が必要になった。

### 2.4 なぜセッションごとに再起動するのか
- 原文が書いていること:`claude -p` は終わると終了する(オペレーターがいないと、通常は途中で止まって入力待ちになる)。ループがその代わりに「次の仕事」を始める。毎回、新しい Docker コンテナ・新しい clone。新しい agent は文脈なしで始まるので、README と進捗ファイルを丁寧に更新させる。
- 別の記事(harness 設計)が書いていること:**context reset**(文脈を空にして新しい agent に引き継ぐ)と **compaction**(会話を要約して同じ agent が続ける)の比較。Sonnet 4.5 では「context anxiety」(上限が近いと早く切り上げる)があり reset が必須だったが、Opus 4.5 で薄れ、reset をやめて自動 compaction に変えた。
- 筆者の推測:セッションが 1 つの仕事の区切りになる、コンテナが綺麗で、止まっても自動で次が起動する。
- **教訓**:harness の部品は「モデルができないこと」の仮説で、モデルが進化したら外せる。

### 2.5 git 同期の限界
| 問題 | 原文の対処 |
|---|---|
| 再起動の代償:新しい agent は自分の位置を把握するのに時間がかかる | README・進捗ファイル |
| merge conflict が頻発 | Claude 自身が解消 |
| 新機能が既存機能を壊す(テキストが merge できても動作は保証されない) | CI を導入し、チェックを厳格に |
| カーネルは分けられない 1 つの巨大タスク | GCC オラクルで分割 |

筆者の推測(原文に無い):agent が落ちると lock が残って古くなる。lock は push に成功してはじめて有効になるので、「先に確保して push、それから作業」の順序が肝心。

### 2.6 GCC オラクルと delta debugging
- **オラクル**:正しい答えを知っている基準。カーネルの大半を GCC でビルドし、一部だけ自作コンパイラでビルドする。壊れたら原因は自作側の少数に絞れる。agent ごとに別のファイルを担当させられる。
- **delta debugging**:失敗する集合を半分ずつ試して最小の原因に絞る手法(git bisect の仲間)。ここでの用途は「**一緒に失敗するファイルの対**」の特定。merge conflict の解決ではない。

### 2.7 時間感覚が弱い、と `--fast`
- Claude は時間の経過が分からず、放っておくと何時間もテストを回す。
- ハーネスは `--fast`(テストの 1% か 10% をランダム抽出)を用意した。サンプルは **agent ごとに固定、機械ごとにランダム**。
  - 固定の理由:同じ agent の前後比較ができる(前は通り、後で落ちたなら今回の変更が原因)。
  - ランダムの理由:agent 全体を合わせるとほぼ全テストを網羅する。
- 限界:自分のサンプル外の壊れは見つけられない。だから後期に CI を足した。

### 2.8 公式機能の agent teams との違い
公式ドキュメント(Agent teams):実験的機能(既定オフ、`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`)。**team lead(= オーケストレーター)が分解・割り当て・集約**し、共有タスクリストはファイルロックで取り合いを防ぐ。推奨は 3〜5 人。同じファイルを複数人で編集すると上書きされる。`-p` では teammate を起動しない。
→ 事例は lead 無し、製品は lead あり。ただし「製品が事例に由来する」とは原文に無いので言わない。

## 3. 評価の分離

### 3.1 自己評価バイアス(ハルシネーションではない)
- **ハルシネーション**:事実を作る(存在しない関数など)。
- **自己評価バイアス**:自分の成果物に甘い採点をする。凡庸でも自信満々に褒める。

### 3.2 harness 設計(planner / generator / evaluator)
同じ「2D のレトロゲームメーカー」で、単独 agent は 20 分・$9(画面は出るが操作に反応せず動かない)、3 役の harness は 6 時間・$200(動く)。evaluator は Playwright で実際に UI を操作して採点する。基準ごとに閾値があり、1 つでも下回れば失敗。「out of the box の Claude は QA が下手」(原文)。
**分離しても寛大さは消えない**(evaluator も LLM)。校正が要る。

### 3.3 evaluator が「失敗」とする基準
基準ごとの閾値を設け、1 つでも下回れば失敗(sprint 単位)。事前に「sprint contract」で合意する。

### 3.4 別の session・別モデルで評価すれば甘くない?
- 同じモデルの新しい session:文脈への思い入れは減るが、**LLM 同士の寛容さは残る**(原文)。
- 別モデル(例:Gemini)での交差レビュー:独立性は高い。ただし機密データ(PHI など)を外部サービスに送らないこと。
- 評価を頼むときの 4 点:元の要件も渡す、誰が書いたかは伏せる、など。

### 3.5 校正(few-shot)と過剰指摘の防止
- **校正**:人間が点数と理由を付けた例を数個見せて、基準を揃える。
- **過剰指摘**:評価者に「問題を探せ」と言えば必ず見つかる。対策:blocker の範囲を限定(正しさ・PHI/セキュリティ・build 破壊・要件違反)/ 原文の引用と証拠を必須に / 確信度 7/10 未満は blocker にしない(上限 5 件)/ 「指摘しないリスト」/ 修正は 1〜2 回まで。
- (`~/.claude/skills/code-review-loop` はこの考え方で作った。引用・確信度・上限などは gstack の review skill を参考にした運用上の工夫で、公式の推奨ではない)

## 4. /goal

出典: Claude Code docs「Keep Claude working toward a goal」

### 4.1 何をするか
完了条件を 1 つ書くと、Claude は条件が満たされるまで、プロンプトなしで作業を続ける。**ターンが終わるたび、別の小さな高速モデルが判定**する:未達(理由を指針に次のターン)/ 達成(解除)/ 不可能(解除)。
実体は **session 限定の prompt 型 Stop hook**。1 session に 1 つ。
公式の言葉:完了を決めるのは、作業しているモデルではなく新しいモデル(= 評価の独立)。

### 4.2 審判は「読むだけ」
評価者はコマンドを実行せず、ファイルも読まない。**会話に出た内容だけ**で判定する。だから条件は「Claude の出力で証明できる形」に書く(「npm test が exit 0」は良く、「コードがきれい」は判定できない)。

### 4.3 良い条件の書き方
1. 測れる終点を 1 つ(テスト結果・build の終了コード・ファイル数・空のキュー)
2. 確認方法(「npm test が exit 0」「git status がクリーン」)
3. 守る制約(「他のテストファイルは変更しない」)
- 上限は条件に書く(「…または 20 ターンで停止」)。最大 4,000 文字。

### 4.4 コマンド
- 設定:`/goal <条件>`(新しいゴールで置き換わる。設定するとすぐ作業が始まる)
- 状況:`/goal`(条件・経過時間・ターン数・トークン・直近の理由)
- 解除:`/goal clear`(別名 stop / off / reset / none / cancel)。`/clear` でも解除。
- 実行中は `◎ /goal active` が表示され、Ctrl+O で判定理由を見られる。

### 4.5 `claude -p "/goal …"` と、対話の `/goal` の違い
**ループの仕組みと審判は同じ**。違うのは「誰が見ていて、どう操作するか」。

| | 対話の `/goal` | `claude -p "/goal …"` |
|---|---|---|
| 実行 | 開いている session の中 | 1 回の起動で、最後まで回して終了 |
| 見え方 | 判定がその場で出る、Ctrl+O で理由 | 既定の出力は**最後の応答だけ**(止まって見える)。`--output-format stream-json --verbose` で逐次表示 |
| 止め方 | `/goal clear` | Ctrl+C |
| 権限の確認 | 対話で答えられる | **答えられない**。事前に許可されていない tool は拒否される。無人で回すなら auto mode など |
| 再試行・見回り | idle check-in や自動リトライがある | check-in はターン終了時のみ |
| 向く場面 | 手元の作業 | CI・cron・スクリプト(例:`claude -p "/goal CHANGELOG.md に今週マージした全 PR のエントリがある"`) |

### 4.6 `/goal` と `/loop` と Stop hook の違い
| | 次のターンが始まるのは | 止まるのは |
|---|---|---|
| `/goal` | 前のターンが終わったとき(条件が未達なら) | 審判が「達成/不可能」と判定、人が直すエラー、`/goal clear` |
| `/loop` | **時間の間隔**が来たとき | 人が止める、Claude が終了と判断(間隔を自分で決める形のとき)、固定間隔は 7 日で期限切れ |
| Stop hook | 前のターンが終わったとき | 自前のスクリプトや prompt が決める |

- **`/goal` = 「いつ終わりか」(条件で駆動)**。1 つの終点に向かって進める。審判は独立したモデル。
- **`/loop` = 「いつ、もう一度走らせるか」(時間で駆動)**。同じことを繰り返す(ポーリング、PR の見守り)。
  - `/loop 5m check the deploy`:5 分ごとの固定間隔
  - `/loop check the deploy`:Claude が毎回 1 分〜1 時間で間隔を決める
  - `/loop`:組み込みの保守プロンプト(または `loop.md`)
  - session 限定、起動中かつ idle のときだけ動く、最小 1 分、1 session に 50 件まで。
- 組み合わせ:auto mode は 1 ターン内の tool の確認を省き、`/goal` はターンごとの確認を省く。
- 別に、session が無くても動かすなら Routines(クラウド)や Desktop の scheduled task。

### 4.7 いつ確定的(決定論)なチェックが要るか。`/goal` だけでは足りないのか
`/goal` の審判は **LLM が会話を読んで判定**する(確率的、寛大になりうる、実行はしない)。次の場面では、決定論的な仕組みを別に持つ。

1. **出ると困る場面**(PHI・セキュリティ・本番デプロイ・データ移行):最後の関門が「LLM の読み取り」に依存してはいけない。CI / pre-commit / hook を最後の砦にする。
2. **やってはいけない操作を止めたいとき**:`/goal` は「いつ止まるか」を決めるもので、**ターンの途中の危険な操作は止めない**。force push、`rm -rf`、commit などは hook・permissions・sandbox の仕事。別の層。
3. **確認の根拠が会話に出ない・大きすぎるとき**:審判はコマンドもファイルも読まない。Stop hook でスクリプトが自分でチェックを走らせる。
4. **再現性・監査・全員への強制が要るとき**:`/goal` は個人が session に打つもので、記録も強制もない。repo の CI や設定の hook は、全員・毎回・Claude 以外の commit にも効く。
5. **コストと速さ**:lint・型チェック・テストは決定論的に安く速く、寛大さもない。LLM の審判は曖昧な条件に残す。

**`/goal` だけでよい**:個人の探索的な作業、見える出力で十分に検証でき、リスクが低く、あとで自分が結果を見る場合。
**実務の組み合わせ**:条件に決定論的な証拠を入れる(「`npm test` が exit 0 かつ `tsc --noEmit` がクリーン」)ので、審判は終了コードを読むだけ。そのうえで最後の関門は CI / pre-commit。

## 5. hook と「貼り紙と鍵」

### 5.1 助言(CLAUDE.md)と決定論(hook)
- **貼り紙(助言)**:CLAUDE.md の規則。モデルが読んで従うが、守られないことがある。
- **鍵(決定論)**:hook・CI・sandbox。条件が合えば毎回必ず実行される。モデルの考えに関係ない。
- 日常のこと(規約、命名)は貼り紙で足りる。出ると困る数件(データ削除、秘密の漏洩)にだけ鍵を足す。

### 5.2 husky・pre-commit・`--no-verify`
- **git hook**:commit の前後に自動で走るスクリプト(`pre-commit` など)。`.git/hooks/` に置くが、`.git` は共有されない。
- **husky**:hook をプロジェクト内の `.husky/` に置いて共有する道具。`npm install` で `core.hooksPath` を設定し、全員が同じチェックを持つ。**lint-staged** は変更したファイルだけに lint を掛ける。
- **`git commit --no-verify`**(短縮 `-n`):pre-commit hook を**飛ばす**。だから pre-commit は「外せる鍵」。本当の最終防衛は **CI で同じチェックをもう一度**走らせること。

### 5.3 この環境に入れた鍵(2026-10-14)
`~/.claude/CLAUDE.md` の 4 ルールを機械的に強制した。

| ルール | 鍵 |
|---|---|
| commit / push | 確認ダイアログ(ask) |
| `--no-verify` 系 | 禁止(deny) |
| worktree | 確認(ask) |
| `*.zh.md` | 禁止(deny)+ グローバル ignore |

- 場所:`~/.claude/settings.json`(permissions と hooks)、`~/.claude/hooks/guard-rules.sh`、テスト `guard-rules.test.sh`(54 件)、`~/.config/git/ignore`。
- 三層:① permissions の規則(スクリプトに依存しない)、② hook(`git -C . push`、`/usr/bin/git push`、`sh -c '…'` などの変形)、③ git 層(ignore)。
- 実機で確認:deny 3 種(`--no-verify`、`HUSKY=0`、`.zh.md` の add)、ask(commit・push・worktree)と変形。**未確認**:EnterWorktree と `Agent(isolation:worktree)` の ask。
- 限界:`eval` や alias など意図的な迂回は止められない。ユーザー自身が端末で打つコマンドには効かない。`grep --no-verify` は誤って deny される。
- 公式仕様:permissions は deny → ask → allow の順で最初に一致したものが勝つ(allow は deny/ask の例外にならない)。hook の失敗・タイムアウトは「通す」扱い(`onFailure:"block"` は v2.1.295 以降)。Bash の規則は書かれたコマンド文字列にしか一致せず、変形は通る。
- **husky v9 化**は一度試したが、指示で元に戻した(welby-phr-web は v8.0.3 のまま)。

## 6. コスト(付録 A)

出典: Claude Blog「What a task costs on Opus 5.5」「Using Claude Code: Spending your effort」(2026-09-25)
- コストを最も動かすのは**キャッシュ命中率**。同じ約 280 万 input token の作業が、キャッシュなしで $11.20、命中率 90% で $1.62、96% で約 $0.99(約 11 倍の差)。
- 会話の前半を書き換える操作(ツール定義やシステムプロンプトの変更)は命中率を下げる。
- effort は「抜け漏れ」を減らすが「方向違い」は直せない。低 effort で実装、高 effort で検証(著者の推奨)。
- 同じトークン量なら Opus 5.5 は約 31% 安い。

## 7. 事故と防御(第 ④ 部)

- **4/23 事後報告**:品質低下の原因は 3 つの小さな変更。3/4 既定 effort を high→medium(4/7 に戻す)、3/26 キャッシュ変更のバグで古い思考を毎ターン消去(4/10 修正)、4/16 冗長さ抑制の prompt(評価約 3% 低下、4/20 に戻す)。教訓:既定値は品質判断、プロンプトは 1 行ずつ検証。
- **auto mode**:承認の約 93% が「許可」だった(確認疲れ)→ 分類器。誤検知 8.5%→0.4%、見逃し 6.6%→17%。「正直な数字」で、丁寧に人間が確認する場合の代わりにはならない。
- **sandbox**(OS レベル):書き込みはワークスペース内、ネットワークは既定で拒否。確認が 84% 減。
- 公式の教訓:最も弱い層は自分で作った層。

## 8. AI の助言の扱い方(今回の学び)

Gemini の助言を何度も精査した。**良い方向でも、細部の事実が間違っていることがある**。

| 助言の内容 | 実際 |
|---|---|
| hook の入力 JSON は `toolName` / `input.command` | 公式は `tool_name` / `tool_input.command`。誤ったままだと空文字が取れ、**何にも一致せず黙って通す** |
| 出力は `{"permissionDecision":…,"reason":…}` | 公式は `hookSpecificOutput` の形式。平らな形は無視される可能性が高い |
| `.hooks.PreToolUse = "bash …"`(文字列) | 配列でなければならない。文字列は不正で、既存の hook も上書きする |
| `push[[:space:]]` で `git push` を検出 | 裸の `git push` に**一致しない**(実測) |
| `-n` を全コマンドで deny | `grep -n`、`head -n` まで禁止してしまう(実測) |
| delta debugging で merge conflict を解決 | 失敗ファイルの対の特定。conflict の解決ではない |
| ハルシネーション | 正しくは自己評価バイアス |

**方針**:助言は鵜呑みにせず、公式ドキュメントと実測で確かめてから採る。セキュリティ用のスクリプトは、**間違った入力でも「通す」のではなく「止める」**(fail closed)ように書き、テストで確かめる。

## 追記(2026-10-15):/goal と /loop の周辺用語と使いどころ

### 用語

- **cron / crontab**:Unix 系 OS の定時実行の仕組み。名前はギリシャ語の「時間(Chronos)」由来とされる。crontab は「cron table(定時実行の表)」。`/loop` は、Claude 向けの定時実行に近い。
- **exit 0**:コマンドが終わったときに返す「終了コード」。**0 は成功、0 以外は失敗**。`npm test` が `exit 0` で終わる = テストが全部通った、という意味で、条件に書くと審判が判定しやすい。
- **claude -p**:`--print` の略。対話画面を開かず、1 回実行して結果を出力して終わる非対話モード。`claude -p "/goal …"` で無人でも最後まで動かせる。
- **ポーリング(polling)**:一定間隔で状態を確認し続けること。`/loop 5m デプロイを確認` はこれに近い。ただし `/loop` はポーリングに限らず、同じ指示の定期的な再実行全般。
- **審判を使わない = Stop hook**:モデルの判定の代わりに、自分のスクリプトで「続けるか止めるか」を決める方法(例:テストを実際に実行し、exit 0 なら止める)。`/goal` は小モデルが会話を読んで判定するのに対し、Stop hook は決定論的に判定できる。

### /goal の役割(「終わりを決める仕組み」)

- `/goal` は考え方(推論やタスク分解)を変えるのではなく、**完了の境界を決める**仕組み。ターンごとに審判が「達成/未達/不可能」を判定する。
- 効果:モデルが「だいたい終わった」と言っても未達なら続く。1 ターンで終わらなくても、人が促さなくてよい。
- ただし「厳しく検査する」のは条件の書き方次第。審判は会話しか読まず、LLM なので寛大になることもある。

### 条件の 3 役割(成功条件・制約・上限)

| 役割 | 答える問い | ないと |
|---|---|---|
| 成功条件(終点 + 確認方法) | 何をもって完了か | 審判が判定できず、止まらないか誤判定する |
| 制約 | 完了までに何を触らないか | 条件だけ満たす抜け道が通る(例:テストを消す) |
| 上限 | いつ諦めるか | 達成できないとき token を使い続ける |

重要度は、成功条件 > 制約 > 上限。ただし無人で回すときは、上限の優先度が制約と同等に上がる。公式の 3 要素は「測れる終点・確認方法・制約」で、上限は条件に足して書くよう勧められている。

### /goal と /loop の使いどころ

| | /goal | /loop |
|---|---|---|
| 向く作業 | 終わる作業(テストが通る、移行完了、型エラー 0、キューが空) | 見続ける作業(デプロイ確認、PR コメント確認、定期メンテ) |
| 次を始めるとき | 条件が未達のとき | 時間が来たとき |
| 完了の判定 | 審判(別の小モデル) | なし(同じことを繰り返す) |
| 期限 | 条件達成まで(上限を条件に書く) | 作成から 7 日で期限切れ |

一言:`/goal` は「いつ終わるか」を決め、`/loop` は「いつ再実行するか」を決める。

### Codex との関係(事実の範囲)

- Codex CLI 0.128.0 で `/goal` が登場(2026-04-30 前後)、Claude Code 2.1.139 で `/goal` が登場(2026-05-11〜12)。約 11〜12 日の差。
- どちらかがどちらかを参考にしたかは、公式に書かれていない。共通の前身は、社区の「Ralph loop」(`while true` で同じ指示を繰り返す方式)。
- 出典は二手の記事が中心。発表前に、両者の公式 changelog で日付を確認する。

### 数字の扱い

- 「/goal は 60% 多く時間・token を使い、30% 完成度が上がる」という数字は、出典を確認できなかった。発表には使わない。使うなら、同じ課題を `/goal` あり・なしで数回ずつ試し、通過率・ターン数・token を測る。

### 条件の優先順位と、審判の仕組み(2026-10-15 追記)

- **成功条件だけだと抜け道が通る**:「npm test が exit 0」だけだと、Claude がテストを削除したり、常に通るように書き換えても条件は満たされる。exit 0 でも価値はない。それを防ぐのが制約。
- **優先順位**:成功条件(土台・必須)> 制約(柵)> 上限(安全網)。ただし無人(`claude -p`・就寝中)で回すときは、止める人がいないので上限も制約と同格に上がる。
- **上限も審判が読む**:公式は「Claude は上限の条項に対して毎ターン進捗を報告し、評価者が会話からそれを判定する」と書いている。つまり上限も会話に出た内容で判定される。(別のハードな計数器があるかどうかは、公式には書かれていない。)
- **審判が別モデルである理由**:公式は「完了の判定は、作業しているモデルではなく、新しいモデルが行う」と書く。狙いは**独立性**(自分で自分を採点しない)であって、「より厳しくする」ことではない。既定では小さな高速モデル(Haiku 系)で、能力が高いとは限らない。厳しさは、条件に書く検査と証拠で決まる。
- **審判がファイルを読まず、コマンドも実行しない理由**:公式は事実として「ツールを呼ばないので、Claude が会話に出したものしか判定できない」と書く。理由は明記されていないので、以下は推測:速く安く回すため(評価コストは「通常のターンに比べて無視できる」と公式)、副作用を持たせないため、そして判定の根拠を会話の中に残すため。
- **最も強い厳しさ**:審判任せにせず、実行できる検査(テスト・lint・build)を条件に入れる。審判は実行できないが、Claude が実行した結果が会話に出るので、判定が客観的になる。

### 審判は会話を信じる — 不正(手抜き)のリスク(2026-10-15 追記)

- 審判はスコアボード(会話)しか見ない。選手(Claude)が実行せずに「通りました」と書くだけでも、審判が信じてしまう可能性がある。公式も、審判が寛大になりうると注意している。
- 対策:条件に「実行して、出力を示す」と書く。さらに強く守りたいときは、Stop hook(自前スクリプトで判定)や CI のように、モデルを介さない検査を併用する。
- たとえ:Claude = 選手、会話 = スコアボード、審判 = 見るだけの人。

### 第 3 ページ(オーケストレーター無し)の読み方

- lock は**ファイル単位ではなくタスク単位**。`current_tasks/` に「このタスクは取った」と書いたテキストファイルを置き、2 つの agent が同じタスクを取ろうとしたら、git の同期で後の方が別のタスクを選び直す。
- 同じソースファイルを複数の agent が触ることはあるので、merge conflict は頻繁に起きる(Claude が自分で解消する)。
- つまり lock が防ぐのは「同じ仕事を二重に取ること」であって、「同じファイルを同時に編集すること」ではない。
