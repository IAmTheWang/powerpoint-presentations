## 本文

### 1. タイトル:/goal に学ぶ agent 設計の判断　`0:00–0:30`

> 🀄 **要点(中文):**今天的主角是 /goal。不是教怎么用,而是借官方文章看它背后的 agent 设计思路(机制、数字、失败案例)。

本日はお時間をいただきありがとうございます。今日の主役は、Claude Code の /goal という機能です。ただし使い方の紹介ではなく、/goal の中にある「agent をどう設計しているか」を、Anthropic の公式ブログと合わせて読み解きます。機能の紹介よりも、仕組みと数字、そして失敗談を中心にします。

### 2. 導入:16 個の Claude が C コンパイラを作った　`0:30–1:30`

> 🀄 **要点(中文):**用 C 编译器案例抓住注意力(16 个 Claude、约 2 周、约 2 万美元、10 万行)。重点不是模型多聪明,而是“周围的机制”;预告主线:给“停不下来的循环”加上终点和审判。

まずこの数字を見てください。Anthropic の研究者が 16 個の Claude を並列に走らせ、ゼロから Rust 製の C コンパイラを書かせました。約 2,000 回の Claude Code セッション、約 2 週間、API コストは約 2 万ドル弱です。結果は約 10 万行で、Linux 6.9 を x86、ARM、RISC-V でビルドでき、主要なコンパイラのテストスイートの 99% を通ります。

ここで注目したいのは、モデルの賢さそのものより「その周りの仕組み」です。人間が頑張ったのはコードではなく、テストと環境の設計でした。今日は、この止まらないループに「終点」と「審判」を付けるとどうなるか、つまり /goal を軸に、公式の記事から 4 つの設計判断を取り出します。

> *補足(任意・聞かれたら):Opus 4.6 での実験で、インターネット接続なしのクリーンルーム実装です。*

<sub>出典: https://www.anthropic.com/engineering/building-c-compiler</sub>

### 3. ① 並列 agent:並列化にオーケストレーターは不要だった　`1:30–3:45`

> 🀄 **要点(中文):**16 个 agent 没有“经理”也能并行:靠 lock(按任务认领,防重复)+ 测试。不是说经理不好,只是这个案例里不需要。注意 lock 是任务级,不是文件级,所以 merge conflict 仍然频繁。

最初の問いです。複数の agent を同時に動かすとき、誰が仕事を割り振るのでしょうか。よくある答えは、管理役のオーケストレーター agent を置くことですが、この事例では置きませんでした。仕組みは驚くほど素朴で、bash のループがセッションの終了ごとに Claude Code を再起動し、毎回新しい Docker コンテナを立てます。共有リポジトリは bare な git で、各 agent は自分の workspace に clone して、終わったら push します。

タスクの取り合いは lock ファイルで防ぎます。agent は current_tasks ディレクトリにテキストファイルを書いてタスクを確保し、2 つの agent が同じタスクを取ろうとしても、git の同期で 2 番目の agent が別のタスクを選び直すことになります。lock はファイル単位ではなくタスク単位で、同じファイルを複数の agent が触ることはあるので、merge conflict は起きます。

オーケストレーター agent がいないので、各 agent が「次に最も明らかな問題」を自分で選びます。merge conflict は頻繁に起きますが、Claude 自身が解消します。

この事例で必要だったのは、オーケストレーターではなく、取り合いを防ぐ仕組みとテストでした。人間のチーム運用とは別物ですが、「小さい単位で取り合いを避け、git で合流させる」という発想は、並行開発の考え方と通じるものがあります。

<sub>出典: https://www.anthropic.com/engineering/building-c-compiler</sub>

### 4. ① 並列 agent:テストが舵 — 検証者が上限を決める　`3:45–5:00`

> 🀄 **要点(中文):**原则 1:验证者(测试)的质量决定成果上限。要为 Claude 设计环境(输出精简、错误写一行、Claude 没时间感所以做 --fast 抽样)。后期新功能弄坏旧功能,才补上 CI。

この事例で著者が最も力を入れたのは、コードではなくテストと環境でした。

1 つ目は検証者の質です。検証がほぼ完璧でないと、Claude は「間違った問題」を一生懸命解きます。2 つ目は Claude 向けに設計すること。出力は数行にして詳細はログファイルへ、エラーは ERROR と理由を同じ行に書いて grep で拾えるようにしました。コンテキストが汚れるのを避けるためです。3 つ目は、Claude は時間感覚が弱いこと。放っておくとテストを何時間も回すので、1% か 10% のランダムサンプルだけ走らせる --fast オプションを用意しました。

限界もあって、終盤は新機能が既存機能を壊し始めたため、CI を後から導入しています。

いまの Claude Code では、/batch や worktree、claude --cloud が、この考え方を製品として使える形にしたものです。

<sub>出典: https://www.anthropic.com/engineering/building-c-compiler / https://code.claude.com/docs/en/best-practices</sub>

### 5. ② 評価の分離:自分の成果物を褒める agent　`5:00–6:30`

> 🀄 **要点(中文):**原则 2:agent 评价自己的成果会过度夸奖(自评偏差),所以把“做”和“评”分开(planner / generator / evaluator)。但分开不会自动变严格,evaluator 也要调教。

2 つ目の判断は、作る agent と評価する agent を分けることです。公式の記事によると、agent は自分の成果物を評価させると、客観的には凡庸な出来でも自信満々に褒める傾向があります。これを「自己評価バイアス」と呼んでおきます。特にデザインのように、テストで白黒がつかない領域で目立ちます。

そこで planner、generator、evaluator に分けました。planner が 1〜4 文の指示を仕様に広げ、generator が sprint ごとに実装し、evaluator が Playwright MCP で実際に動いているアプリを操作して、基準ごとに採点します。sprint の前には、何をもって完了とするかを contract として合意させます。

注意点は、分離しただけで寛大さが消えるわけではないことです。evaluator も LLM なので、最初は問題を見つけても「まあ良いか」と自分を説得して承認してしまいました。ログを読み、懐疑的になるよう prompt を調整する作業が必要でした。

<sub>出典: https://www.anthropic.com/engineering/harness-design-long-running-apps</sub>

### 6. ② 評価の分離:20 分 $9 vs 6 時間 $200　`6:30–7:45`

> 🀄 **要点(中文):**分离的效果与代价:单独 agent 20 分钟 $9,画面有但不能玩;三角色 6 小时 $200,贵 20 倍但差距明显。另一个教训:harness 的每个部件都是“模型单独做不到”的假设,模型进化后要重新检验(Opus 4.6 去掉了 sprint 结构)。

効果と費用の数字です。「2D のレトロゲームメーカー」という同じ 1 文の指示で、単独 agent は 20 分、9 ドル。画面は出ますが、エンティティが表示されるだけで入力に反応せず、ゲームとして動きませんでした。planner、generator、evaluator を使った harness は 6 時間、200 ドルで、20 倍以上のコストです。それでも品質の差は一目瞭然だった、と書かれています。

もう一つ大事な教訓があります。harness の各部品は「モデルが単独ではできないこと」についての仮説だということです。モデルが進化すれば、その仮説は古くなります。実際、Opus 4.6 が出たあとは sprint の構造を外し、planner と evaluator は残しました。

皆さんが agent の仕組みを作るときも、定期的に「この部品は本当にまだ必要か」を問い直すのが良いと思います。

> *補足(任意・聞かれたら):数字は Opus 4.5 でのものです。*

<sub>出典: https://www.anthropic.com/engineering/harness-design-long-running-apps</sub>

### 7. ② /goal:/goal は、ループに終点と審判を付ける　`7:45–9:15`

> 🀄 **要点(中文):**主角登场:/goal = 给 while true 循环加上“终点 + 审判”。设一个完成条件,Claude 自动连续工作;每轮结束由另一个小模型判断(未达成 / 达成 / 不可能)。就是“做与评分开”的产品化。一个会话只能有一个 goal。

ここから、今日の主役の /goal です。最初の事例を思い出してください。C コンパイラの harness は、while true の無限ループでした。終わりがなく、完了を判定する審判もいません。Claude が誤って自分のプロセスを kill してしまい、ループが止まった、という話も書かれていました。

/goal は、このループに「終点」と「審判」を付けたもの、と考えると分かりやすいです。完了条件を 1 つ書くと、Claude はその条件が満たされるまで、プロンプトなしで作業を続けます。ターンが終わるたびに、別の小さなモデルが「条件は満たされたか」を判定します。未達なら、その理由を指針に次のターンが始まります。達成か、不可能と判断された場合に、ゴールが解除されます。

公式は、完了を決めるのは作業しているモデルではなく、新しいモデルだと書いています。これは、さきほどの「作る人と採点する人を分ける」という考え方そのものです。1 つの session に 1 つの goal で、その session 限定です。claude -p に /goal を渡せば、無人でも最後まで動きます。

<sub>出典: https://code.claude.com/docs/en/goal</sub>

### 8. ② /goal:審判は「読むだけ」— 実行はしない　`9:15–11:00`

> 🀄 **要点(中文):**审判只读对话,不执行命令也不读文件(选手 / 记分牌 / 裁判)。所以条件要写成“Claude 的输出能证明”的东西。弱点:Claude 没运行只说“通过了”,审判可能信 → 条件里写“运行并展示输出”。

次に、審判の仕組みで大事な点です。スポーツにたとえると、Claude は選手、会話はスコアボード、審判は見るだけの人です。審判は、条件とここまでの会話を受け取って判定します。コマンドは実行せず、ファイルも自分では読みません。つまり、選手がスコアボードに出した内容だけで判断します。

だから「テストが全部通る」は良い条件です。Claude が実際にテストを走らせ、その結果がスコアボードに出るので、審判が読めます。逆に「コードが良くなった」は、証拠が出ないので判定できません。これは最初の原則、「チェックが甘いと、成果もそこまで」の、/goal での現れ方です。

ただし弱点もあります。審判は会話に書かれたことを信じるので、Claude が実行せずに「通りました」と言うだけだと、見抜けないことがあります。だから条件に、「実行して、出力を示す」と書きます。

評価には小さな高速モデルを使い、費用は通常のターンに比べて小さい、と公式は書いています。実体は、session 限定の prompt 型 Stop hook です。自分で書けば、スクリプトで決定論的に判定することもできます。この点は、あとの hook の話につながります。

<sub>出典: https://code.claude.com/docs/en/goal</sub>

### 9. ② /goal:良い条件の書き方 — 成功条件・制約・上限　`11:00–12:15`

> 🀄 **要点(中文):**条件的三个角色:成功条件(可测终点 + 确认方法)、制约(不能碰什么)、上限(几轮放弃)。每个都配了“没有会怎样”;对比一个坏例子和一个好例子。

では、良い条件はどう書くか。役割で 3 つに整理します。1 つ目は成功条件で、何をもって完了かを、測れる終点と確認方法で書きます。「npm test が exit 0 で終わる」のようにです。ここが曖昧だと、審判が判定できません。2 つ目は制約で、完了までに触ってはいけないものです。「他のテストファイルは変更しない」と書かないと、テストを消して通すような抜け道が通ってしまいます。3 つ目は上限で、「または 20 ターンで停止」のように書きます。ないと、達成できないときに token を使い続けます。公式も、上限を条件に書くことを勧めています。条件は 4,000 文字まで書けます。

スライドの例で言うと、悪い例は「認証まわりを良くして」で、審判には判定できません。良い例は、範囲、確認方法、制約、ターンの上限まで書いたものです。

<sub>出典: https://code.claude.com/docs/en/goal</sub>

### 10. ② /goal:条件の優先順位 — 土台・柵・安全網　`12:15–13:15`

> 🀄 **要点(中文):**优先顺序:成功条件 > 制约 > 上限。只写成功条件会被钻空子(比如删测试)。无人值守时上限升到和制约同级。最严格的做法:把可执行的检查(测试 / lint / build)写进条件。

3 つのうち、順番は成功条件、制約、上限です。成功条件は土台で、なければ審判は感覚で判定するしかありません。制約は柵です。成功条件だけだと、Claude がテストを削除して exit 0 にしても、条件は満たされます。価値はありませんが、通ってしまう。それを防ぐのが制約です。上限は安全網で、品質は決めず、損失の上限を決めます。無人で回すときは、止める人がいないので、制約と同じくらい大事です。上限も審判が会話から読むので、Claude が毎ターン進捗を報告します。最後に、本当に厳しくするなら、審判任せにせず、テストや lint、build のような実行できる検査を条件に入れてください。

<sub>出典: https://code.claude.com/docs/en/goal</sub>

### 11. ② /goal:デモ(録画を再生)　`13:15–15:00`

では、録画をご覧ください。小さなサンプル repo で、条件を書いて /goal を設定します。見てほしいのは 3 点です。1 つ目、設定するとすぐ作業が始まり、別のプロンプトは要りません。2 つ目、ターンが終わるたびに審判の判定が出て、未達のときはその理由が次の指針になります。Ctrl+O で理由を見られます。3 つ目、条件が満たされると自動で解除されます。/goal だけを打つと、経過時間、ターン数、トークン使用量、直近の理由が見られます。

### 12. ② /goal:使いどころ — 終わる作業は /goal、見続ける作業は /loop　`15:00–16:15`

> 🀄 **要点(中文):**/goal 用于会“完成”的工作(测试全过、迁移完成、类型错误 0);/loop 用于要“盯着”的工作(部署、PR 评论)。区别:下一轮由谁触发(条件未达 vs 时间到)、有无审判;/loop 7 天过期。

では、どんな場面でどちらを使うか。/goal は「終わる作業」、/loop は「見続ける作業」です。/goal は、テストが全部通る、旧 API からの移行が完了する、型エラーが 0 になる、といった終点のある作業に使います。/loop は、デプロイの状況を 5 分ごとに確認する、PR に新しいコメントが付いたか見る、といった、時間とともに状況が変わるものを見続ける作業です。ポーリング、つまり一定間隔で状態を確認し続けることに近い使い方です。

決定的な違いは 2 つあります。1 つ目は、次をいつ始めるか。/goal は条件が未達のときに続き、/loop は時間が来たときに始まります。2 つ目は審判の有無。/goal には完了を判定する審判がいて、/loop には完了の判定がなく、同じことを繰り返すだけです。また /loop は、7 日で期限切れになります。

<sub>出典: https://code.claude.com/docs/en/goal / https://code.claude.com/docs/en/scheduled-tasks</sub>

### 14. ③ hook と Mods:Mods — hook の先を自分で作る　`16:30–18:00`

> 🀄 **要点(中文):**hook 的延伸:plugin 里常驻的 JS/TS 模块,能观察、改写、响应 tool 调用,还能画 UI。/goal 本身就是 hook 做的。注意:权限和你本机一样,装之前读源码。

ここからは hook と mods の話です。さきほどの /goal は hook でできていました。その hook の先を、自分で作れるのが mods です。10 月 1 日に公開されたばかりで、Claude Code 2.1.287 以降が必要です。mod は plugin に入れる JavaScript か TypeScript のモジュールで、セッション中ずっと常駐し、状態を持てます。

できることは 3 つです。観察、つまり tool 呼び出しやプロンプト送信、ターンの開始と終了を見ること。書き換え、たとえば危険なコマンドを安全な形に差し替えて次へ渡すこと。そして応答、つまり deny で拒否したり、自前の結果を返したりすることです。

UI も描けます。status line や pane、toast、プロンプトの上の band などです。公式は、AGENTS.md 対応と /diff パネルが mod として作られていると書いています。ソースは anthropics/claude-code リポジトリの mods ディレクトリにあります。

<sub>出典: https://claude.dev/blog/getting-started-with-claude-code-mods/</sub>

### 15. ③ hook と Mods:助言は貼り紙、決定論は鍵　`18:00–20:00`

> 🀄 **要点(中文):**原则 3:CLAUDE.md = 告示(可能被无视),hook / CI = 锁(每次必执行)。重要规则放“锁”这一侧。pre-commit 能被跳过(git commit 的跳过选项),所以最后一道是 CI。

ここで 1 つ整理したい区別があります。CLAUDE.md は助言、hook は決定論です。たとえば CLAUDE.md に「コミット前に lint を実行して」と書くと、モデルが読んで従いますが、守られないことがあります。一方、多くのプロジェクトにある husky の pre-commit hook は、コミットのたびに lint と型チェックを自動で実行し、失敗すれば commit できません。モデルがどう考えていても、毎回必ず走ります。これが決定論です。図のとおり、左の貼り紙は、読むかどうかが相手次第で、すり抜けることがあります。右の鍵は、モデルがどう考えていても通れません。

使い分けの目安は、「守られないと困るもの」は決定論の側に置くことです。ただし pre-commit は git commit の --no-verify で飛ばせてしまうので、本当の最終防衛は CI で同じチェックをもう一度かけることです。Claude の hook や mod は、公式の例で言えば rm -rf や force push のような危険なコマンドを実行前に止める、agent 向けの補強と位置づけると整理しやすいと思います。

最後に注意です。mod は Claude Code と同じ権限であなたのマシン上で動き、書いたのは Anthropic ではなく発行元です。パッケージと同じ扱いで、ソースを読んでから、信頼できる人のものだけを入れてください。

### 16. ④ 事故と防御:品質低下の原因は 3 つの小さな変更　`20:00–21:45`

> 🀄 **要点(中文):**4/23 事后报告:品质下降的原因不是模型,而是产品侧 3 个小改动(默认 effort 调低、缓存 bug、加了简洁的 system prompt)。教训:默认值是质量决策;要测长会话和恢复的会话;prompt 一行一行去掉来测效果。

4 つ目は失敗から学ぶ話です。4 月 23 日に Anthropic が、Claude Code の品質低下の報告について事後報告を出しました。原因はモデルではなく、製品側の 3 つの小さな変更でした。

1 つ目、3 月 4 日に、遅延を減らすため既定の reasoning effort を high から medium に下げました。「賢くなくなった」という声が続き、4 月 7 日に戻しています。

2 つ目、3 月 26 日のキャッシュ関連の変更です。1 時間以上アイドルしたセッションで古い思考を 1 回だけ消すはずが、バグで毎ターン消え続けました。そのせいで Claude が健忘で繰り返しに見え、使用量の消費も増えました。4 月 10 日に修正されています。

3 つ目、4 月 16 日に冗長さを抑える system prompt を足したところ、他の変更と合わさって品質が落ち、ある評価で約 3% の低下が出ました。4 月 20 日に戻しています。

教訓は 3 つです。既定値は性能調整ではなく品質の判断であること。長いセッションや再開したセッションも試験すること。prompt は 1 行ずつ外して効果を測ること。

### 17. ④ 事故と防御:多層防御 — 承認ではなく環境で守る　`21:45–23:00`

> 🀄 **要点(中文):**用户 93% 的权限确认直接点同意(确认疲劳)→ 先上 OS sandbox(确认减少 84%),再叠 auto mode 分类器。诚实的数字:误报 8.5%→0.4%,但漏掉真正的过度行为 6.6%→17%。可靠的是环境层,模型层只是其中一层。

最後に防御の話です。Claude Code の利用者は、権限の確認の約 93% を許可していました。確認が多すぎて、実質的に見ていない。これが確認疲れです。そこで公式はまず OS レベルの sandbox を入れました。書き込みはワークスペース内だけ、ネットワークは既定で拒否です。これで確認が 84% 減っています。

そのうえで auto mode という分類器を重ねました。2 段階で、高速なフィルタが疑わしいものだけを推論に回します。誤検知は 8.5% から 0.4% に下がります。ここで正直な数字を見てください。実際の過剰行動の見逃し率は 6.6% から 17% に上がります。公式自身がこれを「正直な数字」と書いていて、丁寧に人間が確認している場合の代わりにはならない、とも述べています。

つまり、確実なのは環境の層で、モデルの層は多層防御の 1 枚です。もう 1 つ、公式の教訓として、最も弱いのは自分で作った層だと書かれています。

### 18. 議論:3 つの原則と、議論したいこと　`23:00–30:00`
